# 2GIS Parser — сборщик данных о заведениях из 2GIS

Собирает из 2GIS карточки организаций с **телефонами, часами работы, адресом,
координатами, рубриками и рейтингом** — по любому городу и любой теме. Работает через
настоящий браузер, поэтому получает те же данные, что видит обычный посетитель сайта,
включая те, которых нет в SSR-разметке.

**Перенастраивается на свою задачу двумя строками в `config.yaml`** — код трогать не нужно:

```yaml
collect:
  country: kz
  regions: [almaty]
  queries: ["автомойка", "шиномонтаж", "детейлинг"]
```

Механика сбора от темы не зависит: банкетные залы, автомойки, стоматологии, ветклиники,
барбершопы — собираются одинаково. Подробно — в разделе
[«Переделать под свою задачу»](#переделать-под-свою-задачу).

## Готовый кейс: площадки для мероприятий по Казахстану

Проект написан под конкретную задачу — базу заведений, где можно проводить мероприятия
(тойханы, банкетные и конференц-залы, лофты, базы отдыха, рестораны с банкетными залами).
Для них дополнительно вытаскивается **вместимость зала** и считается балл пригодности.

**Алматы собран полностью:** 12 931 организация, из них 6 050 подходят под мероприятия;
телефон есть у 89%, вместимость — у 86% площадок. Прогон занял 3 часа 2 минуты на
8 окнах браузера. Остальные 18 регионов собирает команда — см.
[PROMPT-AGENT.md](PROMPT-AGENT.md).

Вместимость никогда не додумывается: если 2GIS её не отдал — поле пустое.

## Быстрый старт

```bash
git clone <адрес репозитория>
cd 2gis-parser
pip install -r requirements.txt

python run.py doctor     # проверит машину и скажет, сколько окон открывать
python start.py          # мастер: выбрать регион, число окон, запустить
```

Нужен установленный **Google Chrome** (подойдут Chromium, Brave или Microsoft Edge —
ищутся автоматически). `playwright install` выполнять **не нужно**: мы подключаемся
к обычному системному браузеру, а не к сборке Playwright.

Нужен **Python 3.10 или новее**.

### На какой ОС работает

| ОС | Статус |
|---|---|
| Windows 10/11 | Проверено на реальных прогонах — здесь собран Алматы |
| macOS (Intel и Apple Silicon) | Поддерживается: пути к Chrome, запуск процессов и сигналы кросс-платформенные. Первый прогон стоит начать с небольшого региона |
| Linux | Поддерживается так же, как macOS. Нужен графический сеанс: без него останется только `--headless`, а он заметно повышает риск попасть на защитную страницу 2GIS |

Платформозависимого кода в проекте нет: пути собираются через `pathlib`, браузер ищется
по списку кандидатов для всех трёх систем, воркеры запускаются через `subprocess` тем же
интерпретатором, которым запущен `run.py`.

## Как это устроено

Прямой HTTP к 2GIS не работает: сайт отдаёт JS-челлендж. Поэтому поднимается настоящий
Chrome с `--remote-debugging-port`, к нему подключается Playwright по CDP, и мы читаем те же
запросы, которые делает сам сайт. Телефоны и вместимость лежат только в ответе
`catalog.api.2gis.*/3.0/items/byid`, который сайт делает при открытии карточки — поэтому
карточки приходится открывать.

Сбор идёт в две фазы, обе разбираются из общей очереди в SQLite:

**Фаза A — обход.** Открывается рубрика каталога (`/almaty/rubric/10803`) или поисковый
запрос (`/almaty/search/тойхана`), выдача листается до конца, из неё выписываются
идентификаторы заведений. Ничего не открывается — только листание.

**Фаза B — карточки.** Каждое найденное заведение открывается ровно один раз за прогон,
сколько бы рубрик и запросов его ни нашли, и из перехваченного ответа берутся все поля.

Такое разделение и даёт основную экономию: одно заведение попадает в выдачу по десятку
источников, а карточка открывается однократно.

Скелет покрытия — рубрики каталога 2GIS (`src/venues2gis/rubrics.py`, 60 штук в двух
наборах). Это замкнутое множество, определённое самим справочником, поэтому покрытие по
ним проверяемо. Поисковые слова (`src/venues2gis/queries.py`, 80 штук в четырёх языковых
слоях) добирают «расширенные» результаты — например, ресторан со словом «банкет» в
описании, который лежит в рубрике «Рестораны».

Подход взят из [interlark/parser-2gis](https://github.com/interlark/parser-2gis) (LGPL-3.0):
настоящий Chrome, CDP, перехват `items/byid`. Здесь он переписан под задачу — с очередью,
двумя фазами, докачкой после перезапуска, дедупликацией и нормализацией.

## Команды

```bash
python run.py doctor                     # проверка машины и рекомендация по числу окон
python run.py regions                    # регионы: коды, объём, что уже собрано
python run.py collect --region shymkent  # сбор по региону
python run.py collect                    # все 19 регионов подряд
python run.py status                     # состояние очереди
python run.py export                     # пересобрать выгрузку из сырых данных
python run.py pack                       # упаковать свои результаты для отправки
python run.py merge from-Айдара.zip      # влить чужие результаты в свою базу
python run.py probe                      # техническая разведка 2GIS
```

Полезные флаги `collect`:

| Флаг | Смысл |
|---|---|
| `--region taraz --region atyrau` | только эти регионы |
| `--workers 6` | сколько окон браузера поднять (по умолчанию из `config.yaml`) |
| `--max-seconds 28800` | остановиться через 8 часов — удобно для ночного прогона |
| `--rubric-set core` | только «заведомо площадки», без общепита: втрое быстрее |
| `--layer rubric` | только рубрики, без поисковых слов |
| `--max-pages 5` | не глубже N страниц выдачи на задачу (для пробы) |
| `--plan-only` | составить очередь и выйти, ничего не собирая |
| `--refresh-regions` | обновить список регионов с `data.2gis.com` |
| `--headless` | без окна браузера. **Повышает риск антибота**, по умолчанию выключен |

**Ctrl+C — корректная остановка.** Текущая карточка дописывается, прогресс сохраняется,
повторный запуск продолжает ровно с того места, где остановились. Прогон можно рвать
и продолжать сколько угодно раз.

## Сколько это занимает

Замер на 8 ядрах / 32 ГБ, 8 окон браузера, `tools/bench_workers.py`:

| Окон | Карточек в секунду |
|---:|---:|
| 2 | 0,78 |
| 4 | 1,23 |
| 6 | 1,66 |
| 8 | 2,07 |
| 12 | 2,05 |
| 16 | 1,95 |

Скорость упирается в число физических ядер, дальше идёт плато и спад. Антибот 2GIS за все
прогоны, включая 210 страниц подряд, не сработал ни разу — ограничитель это процессор,
а не защита сайта. `python run.py doctor` считает подходящее число окон сам.

Ориентиры по регионам (`python run.py regions` покажет актуальные):

| Регион | Организаций в 2GIS | Время на 8 окнах |
|---|---:|---:|
| Алматы | 43 744 | 3,0 ч (факт) |
| Шымкент | 26 194 | ~1,8 ч |
| Астана | 26 139 | ~1,8 ч |
| Кокшетау | 6 855 | ~0,5 ч |

Все 18 оставшихся регионов на одной машине — примерно 13–16 часов. Разделив их между
четырьмя-пятью людьми, получаем по 3 часа на каждого, то есть одну ночь.

## Работа командой: кто что собирает и как всё свести

1. Координатор раздаёт регионы — по одному-два на человека (`python run.py regions`).
2. Каждый запускает `python start.py`, выбирает свой регион и оставляет машину работать.
3. По окончании мастер сам пересобирает выгрузку и предлагает упаковать результат:
   получается файл `kz-venues-<регион>-<дата>.zip`.
4. Архивы отправляют координатору.
5. Координатор вливает их в общую базу:

```bash
python run.py merge from-Айдара.zip from-Динары.zip
python run.py export
```

Слияние идемпотентно: один и тот же архив можно влить дважды, дубликатов не появится.
Внутри архива лежат сырые ответы 2GIS (`data/raw/*.jsonl`) и состояние очереди —
этого достаточно, чтобы координатор пересобрал общую выгрузку целиком.

## Что получается на выходе (`out/`)

| Файл | Содержимое |
|---|---|
| `venues.csv` / `venues.jsonl` / `venues.xlsx` | Итоговая база площадок |
| `venues_all.csv` / `venues_all.jsonl` | Все собранные организации, без фильтра по пригодности |
| `report.md` | Заполненность полей, покрытие по источникам, разбивка по городам |
| `summary.md` | Сводка по категориям: сколько площадок, телефонов, медианная вместимость |
| `category_stats.csv` | То же в машиночитаемом виде |
| `discovered_rubrics.csv` | Все встреченные рубрики — источник идей для следующей итерации |
| `possible_duplicates.csv` | Пары, похожие на дубли, для ручной проверки |

Состав колонок и правила заполнения — в [docs/DATA-FORMAT.md](docs/DATA-FORMAT.md).

Выгрузку можно пересобирать сколько угодно раз: `run.py export` работает без браузера,
целиком из сырых JSONL, поэтому правила нормализации можно менять задним числом.

## Переделать под свою задачу

Что задаётся конфигом, без единой строки кода:

| Что | Как |
|---|---|
| **Тема сбора** | `collect.queries: ["автомойка", "шиномонтаж"]` — свои поисковые слова |
| **Рубрики каталога** | `collect.rubrics: ["10803", "161"]` — ID видно в адресе: `/almaty/rubric/10803` |
| **Города** | `collect.regions: [almaty, shymkent]` или `--region almaty` |
| **Другая страна** | `collect.country: uz` плюс `--refresh-regions` — у 2GIS 204 региона в 17 странах, домен `2gis.kz` / `2gis.ru` подставляется по региону сам |
| **Скорость** | `collect.workers`, задержки между действиями, глубина пагинации |

То же самое разово, без правки файла:

```bash
python run.py collect --region almaty --query "автомойка" --query "шиномонтаж"
python run.py collect --region astana --rubric 10803 --rubric 17379
```

Проверено на практике: тема «автомойки и шиномонтаж» в Кокшетау собралась тем же кодом —
47 организаций, часы работы у 100%, телефоны у 77%, координаты у 100%.

**Что при этом остаётся в коде** (нужно, только если хотите менять саму логику):

| Файл | За что отвечает |
|---|---|
| `classify.py` | Балл пригодности под мероприятия. Для чужой темы он просто не сработает и ничего не испортит: в `venues.csv` попадают все собранные организации |
| `capacity.py` | Разбор вместимости зала. Для чужой темы поле останется пустым |
| `normalize.py` | Состав колонок выгрузки. Общие поля — название, телефоны, адрес, часы, координаты, рубрики, рейтинг — собираются для любой организации |
| `rubrics.py`, `queries.py` | Встроенные наборы под кейс площадок. Ваши списки из конфига их полностью заменяют |

Иначе говоря: **сбор и нормализация универсальны, предметная надстройка — только
вместимость и балл пригодности**, и она не мешает чужим задачам.

Как искать рубрики под свою тему: запустите сбор по паре слов, откройте
`out/discovered_rubrics.csv` — там все встреченные рубрики с числом заведений.
Дальше берите их ID в `collect.rubrics`, и покрытие станет проверяемым: рубрика —
замкнутое множество, определённое самим 2GIS, в отличие от поисковых слов.

## Известные ограничения

- **Лицензия.** Сбор из веб-версии противоречит пользовательскому соглашению 2GIS.
  Для проверки гипотезы и внутренней работы база годится, для коммерческого запуска
  чистый путь — платный Places API с доступом к `contact_groups` либо выгрузка через
  `data.2gis.com`. Вопрос стоит закрыть до публичного релиза.
- **Обновление данных.** Реестр `seen` защищает от повторного открытия карточек настолько
  надёжно, что перечитать уже собранное заведение нечем — флага сброса пока нет.
- **`--headless`** заметно повышает риск попасть на защитную страницу. По умолчанию
  браузер работает с окном.
